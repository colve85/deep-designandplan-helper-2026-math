# 단원 자료 작성 안내

단원을 추가하거나 다른 과목으로 확장할 때 보는 문서입니다.
`src/UnitsCommonMath1.gs` 의 항목 하나를 복사해 고치는 것이 가장 빠릅니다.

## 단원 하나의 구조

```js
{
  id: 'cm1-01',                       // 저장소 안에서 겹치지 않는 값
  subject: '공통수학1', area: '다항식', name: '다항식의 연산',
  standards: [
    { code: '10공수1-01-01', text: '다항식의 사칙연산의 원리를 설명하고, 그 계산을 할 수 있다.' }
  ],
  ex: { /* 0~3단계 설계 예시 — 아래 표 참고 */ },
  lessons: [ /* 내용 요소별 수업 소재 — 아래 표 참고 */ ]
}
```

과목을 새로 만들었다면 `Code.gs`의 `getAllUnits_()`에 배열을 추가하고, `lib/gas-runtime.js`의 `GAS_FILES`에도 파일명을 등록합니다. 현재 추가 과목 예시는 `src/UnitsExtendedMath.gs`에 있습니다. 공식 원문이 아닌 목표는 `standardStatus: "draft"` 및 원문이 아니라는 표시를 붙입니다.

```js
function getAllUnits_() {
  return [].concat(UNITS_COMMON_MATH_1, UNITS_COMMON_MATH_2, UNITS_ALGEBRA);
}
```

## `ex` — 단계별 설계 예시

키 이름은 `Stages.gs` 의 `fields[].key` 와 정확히 같아야 합니다.
하나라도 비어 있으면 `node tools/verify.js` 가 실패합니다.

| 단계 | 키 | 무엇을 쓰나 |
|---|---|---|
| 0 | `bigIdea` | 핵심 아이디어. 교육과정 축자를 채택하거나 세 범주 분해로 재구성 |
| 0 | `categories` | 내용 체계 세 범주 — 지식·이해 / 과정·기능 / 가치·태도 |
| 0 | `competency` | 인간상 · 총론 핵심역량 · 교과 역량 (선택과 집중) |
| 0 | `interpret` | 성취기준 다시 읽기 — 성취기준 → 해설 → 적용 시 고려 사항 |
| 0 | `misconception` | 학생이 흔히 갖는 오개념 |
| 1 | `understand` | 영속적 이해 — "학생은 ~임을 이해한다" |
| 1 | `canDo` | 세 범주 세부 학습 목표 (관찰 가능한 동사) |
| 1 | `essential` | 핵심 탐구 질문 — 단원을 관통하는 개방형 질문 하나 |
| 1 | `guiding` | 탐구(안내) 질문 5~7개 — 사실 → 개념 → 논쟁·성찰 순 |
| 1 | `intent` | 단원명과 수업 의도 — 배경 → 방향 → 핵심 목표 → 경험 예고 → 기대 성장 |
| 2 | `elements` | 핵심 평가요소 3~5개. 각 요소에 세 범주 표시 |
| 2 | `task` | 수행과제 (GRASPS로 발상) |
| 2 | `evidence` | 수집할 증거 (수행과제 밖의 기타 증거 포함) |
| 2 | `plan` | 평가 계획 — 형성평가 시점과 총괄 시점 |
| 2 | `rubric` | 분석적 루브릭 3수준(우수·보통·미흡) 또는 4수준(매우 우수·우수·보통·향상 필요) |
| 2 | `feedback` | 피드백·자기평가 계획 (for · as) |
| 3 | `phases` | 단원 개관 — 발견 · 탐색 · 적용 · 수행에 차시 배분 |
| 3 | `flow` | 차시 흐름 |
| 3 | `activity` | 탐구·토론 활동 (저진입 · 고천장) |
| 3 | `treatment` | 오개념별 처치 발문 — 학생의 말과 교사의 한 문장을 짝지어 |
| 3 | `support` | 도달을 돕는 지원 전략 |
| 3 | `balance` | 탐구로 볼 것과 연습(드릴)으로 볼 것의 경계 |

`rubric`은 선택한 3수준 또는 4수준의 명칭을 포함해야
설계 점검이 수준 누락을 잡아냅니다. 최하 수준도 "못한다"가 아니라 그 수준에서 실제로
관찰되는 수행으로 씁니다.

여러 줄은 `\n` 으로 잇습니다. 저장소의 기존 항목은 읽기 좋게 줄마다 문자열을 이어 붙여 두었습니다.

```js
understand: '학생은 ~임을 이해한다.\n' +
            '학생은 ~임을 이해한다.',
```

## `lessons` — 내용 요소별 수업 소재

`Stages.gs` 의 `LESSON_COLUMNS` 가 화면의 차시별 설계표 열을 정의하며,
`lessons` 항목의 키와 1:1로 대응합니다.

| 키 | 열 이름 | 쓰는 요령 |
|---|---|---|
| `phase` | 학습 단계 | `발견하기` · `탐색하기` · `적용하기` · `수행 및 성찰` 중 하나 (`Stages.gs` 의 `LESSON_PHASES`) |
| `element` | 내용 요소 | 성취기준을 실제 수업 단위로 쪼갠 이름 |
| `periods` | 차시 | `1차시`, `1~2차시` |
| `material` | 수업 소재 | **학생이 실제로 마주할 자료와 맥락.** 학교·지역·생활 자료가 좋습니다 |
| `open` | 여는 질문 | 탐구를 여는 한 문장. 답이 바로 나오지 않아야 합니다 |
| `goal` | 도달 목표 | 이 차시에서 학생이 도달할 상태 |
| `evidence` | 확인할 증거 | 무엇을 보면 도달했다고 볼 것인가 (말·글·풀이·오류) |
| `activity` | 학생 활동 | 학생이 실제로 하는 일 |
| `tool` | 도구 | 교구, 공학 도구, 학습지 |

작성할 때의 기준은 네 가지입니다.

1. **소재가 구체적인가** — "실생활 상황"이 아니라 "학교 축제 부스 예산표"처럼 적습니다.
2. **목표와 증거가 서로 대응하는가** — 목표가 "설명한다"이면 증거도 설명하는 장면이어야 합니다.
3. **누구나 출발할 수 있는가** — 직관적 단서로 시작해 협력적 정당화로 올라가게 설계합니다.
4. **네 단계를 덮는가** — 최종 수행과제에서 거꾸로 물어 배치합니다. 수행하려면 무엇을 적용해야
   하고, 적용하려면 무엇을 탐색해야 하며, 탐색하고 싶어지려면 무엇을 발견해야 하는가.

한 단원에 4개를 권합니다(발견·탐색·적용·수행 각 하나). `verify.js` 는 2개 미만이면 실패로 보고,
설계 점검은 네 단계 중 두 개 이상이 비어 있으면 확인을 요청합니다.

## 단계 구성 자체를 바꾸려면

`Stages.gs` 의 `STAGES` 를 고칩니다. 단계를 더하거나 필드를 바꾸면
모든 단원의 `ex` 키도 함께 맞추어야 합니다. 바꾼 뒤에는 반드시 확인하세요.

```bash
node tools/verify.js
```

`checklist` 는 그 단계의 자가 점검 문항이며, AI 프롬프트에도 함께 들어가
초안이 그 기준을 향하도록 합니다.
